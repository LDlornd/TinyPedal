# 驾驶数据记录与导出

在“工具 → 驾驶数据记录与导出”打开记录窗口。此功能支持现有游戏的统一读取接口，以及 LFS 的完整物理快照；只有点击“开始记录”后才写驾驶数据。

## 记录一组可比较的数据

1. 先进入游戏驾驶，确认 TinyPedal 接口已经收到有效数据。使用 LFS 时，先完成 [LFS 配置](lfs.zh-CN.md)，填写当前赛道和可确定的车辆参数。
2. 填写驾驶者昵称、本组对照名称，以及想改善的驾驶现象。建议备注包含游戏版本、赛道布局、轮胎类型与状态、初始燃油、天气、设备和辅助设置。
3. 如有需要，选择当前车辆的 `.set` 或 `.svm` 调教文件。程序只复制一份到分析包，最多 16 MiB，并保存 SHA-256；不会修改原文件，也不自动解释其中的调教参数。
4. 选择输出目录和采样间隔，默认 20ms，范围 10–1000ms。点击“开始记录”，预期采样数持续增加。
5. 驶过几圈后点击“停止记录”，再点击“导出分析包 ZIP”。原始 CSV 和元数据仍留在独立记录目录中。

关闭记录窗口、重启或切换 API 会先结束当前记录。检测到赛道、车型、游戏驾驶者或玩家索引变化时，也会结束记录，停止原因可在窗口和元数据中查看。暂停或短暂断流只会留下中断标记，恢复后可以继续同一轮记录。

每次开始都会创建 `drive_UTC时间_随机后缀` 子目录，已有记录不会覆盖或自动清理。窗口只提供本次启动后的最近一轮 ZIP 导出；程序重启后，旧目录仍可直接查看或自行压缩。

## 分析包内容

| 文件 | 用途 |
| --- | --- |
| `samples.csv` | 固定英文字段的逐次采样，UTF-8 BOM，可用 Excel、Python 等工具读取 |
| `metadata.json` | 驾驶者、对照名称、备注、游戏/赛道/车型、会话信息、单位与字段解释 |
| `events.jsonl` | 开始、数据不可用/恢复、不连续、推断圈界及结束事件，每行一个 JSON |
| `summary.json` | 样本数、跳过的重复轮询数、各通道有效值数量与范围 |
| `README.txt` | 随包附带的时间、缺失值和比较口径 |
| `setup.set` / `setup.svm` | 仅在主动选择调教文件时附带 |

ZIP 中只包含该记录目录的这些数据文件，不包含游戏连接密码、整个预设目录或其他记录。

## 字段与时间口径

完整字段表随每轮记录写入 `metadata.json.fields`。常用字段如下：

| 字段 | 含义 |
| --- | --- |
| `recorded_utc` | 本机采样时间，UTC ISO 8601 |
| `elapsed_s` | 本轮开始后的单调时钟秒数，包含暂停和断流 |
| `source_time_s` | 游戏源时钟，可能重置、回绕或受回放影响 |
| `source_generation` | 适配器重置计数 |
| `segment_index` / `break_before` | 连续记录段及此前是否中断 |
| `lap_segment` | 本轮观察到的圈段序号，不是官方比赛圈数 |
| `lap_completed` / `lap_time_s` | 游戏报告的圈数和当前圈时，LFS 未提供 |
| `lap_distance_m` / `lap_progress` | 圈内距离（米）和进度（比例） |
| `speed_m_s` / `rpm` / `gear` | 速度、发动机转速、挡位；挡位 -1=R，0=N |
| `throttle_raw` / `brake_raw` / `clutch_raw` / `steering` | 游戏读取接口提供的输入，未经本记录器平滑 |
| `suspension_fl_mm` 等 | 四轮悬架压缩量，统一 FL、FR、RL、RR 顺序 |
| `load_fl_n` / `slip_angle_fl_rad` 等 | 轮胎载荷和滑移角，具体可用性取决于游戏接口 |
| `raw_*` | LFS 协议原始轴和姿态，可与适配后的通道核对 |

CSV 空值表示接口未提供、该次数据失效或值不合法；零值仍然是有效测量，不用空值代替零。整个 CSV 使用同一列集合，某个游戏不支持的通道会保持空白。`summary.json.available_sample_counts` 可以帮助区分“整个接口没有该通道”和“只有部分时间缺失”。

记录器不插值、不补零、不平滑，也不把重复读取同一源时钟当成新样本。默认 20ms 是请求间隔，不代表游戏或设备的真实报告率；实际间隔应从相邻行计算。超过 250ms 的源时钟或本机采样间隔、源时钟倒退、适配器重置和数据不可用都会产生不连续段，不能跨段求导或插值。每次不连续也会开始新的圈段，避免把两段不完整数据接成完整圈。

LFS 使用单次不可变物理快照，并合并时间差不超过 250ms 的有效 OutGauge 数据；没有重采样。其他游戏沿用原有读取接口，逐项读取期间游戏可能更新数据，因此不保证所有列来自同一物理帧。元数据的 `capture_consistency` 会注明采用哪种方式。

## LFS 圈界与调教分析边界

没有 InSim 时，LFS 的 `lap_completed`、`lap_time_s` 和 `last_lap_time_s` 保持空白。记录器仅通过连续数据中的圈内距离回绕推断新圈段：已知赛道长度时，从最后 20% 进入最前 20%；未知长度时，从大于 100 米进入小于 50 米。

这不是官方计时。传送、出站或倒车也可能满足条件，首尾圈和中断后的圈通常不完整，不能据此判断有效圈或最佳圈。旧版 OutSim 没有圈内距离，因此不会推断 LFS 圈界。

LFS 的胎内空气温度与胎面温度、胎体温度不同；最大可用发动机扭矩与实际输出扭矩不同；悬架压缩量与离地高度也不同。缺失通道不会用近似指标代填。油箱容量、方向盘转角和赛道长度等人工设置在元数据中单独列出。

建议在相同游戏、车辆和赛道布局下比较，保持轮胎、燃油、天气和辅助设置一致，每次只改变一个因素。按完整圈的相同距离对齐数据后，可以比较刹车释放、补油时机、转向修正、速度、载荷和悬架变化。不同游戏的坐标、转向和离合方向可能不同，不宜直接混合。

需要调教建议时，可以把两份 ZIP 一起发给分析者，并说明当前设置、入弯/弯中/出弯的具体问题，以及哪些参数已经改过。数据能够帮助定位现象，但不足以单独确定因果。

## 执行流程与后续修改

`ui/driving_recording.py` 收集输入，调用应用创建的 `DrivingRecorder.start`。记录器持有这轮使用的读取接口和元数据，后台线程调用 `telemetry_sample.sample_reader`，持续写入 CSV 和事件文件。停止时先关闭文件，再写摘要与最终状态，最后才允许 ZIP 导出。API 的停止入口会先等待记录器结束，再关闭游戏连接。

- 新增或调整导出字段：从 `telemetry_sample.py` 的 `CHANNELS` 和 `sample_reader` 入手，字段名、单位和解释集中在这里。
- 需要完整原子快照的后端：在 `APIDataReader.capture` 提供返回 `TelemetryFrame` 的函数；LFS 的实现是 `lfs_reader.State.capture`。其他后端仍可使用现有逐项读取方法。
- 修改写入格式、分段规则或打包内容：调整 `driving_recording.py`，不用修改界面或游戏解码器。
- 修改交互：调整 `ui/driving_recording.py`，中文文案继续放在 `i18n.py`。

文件写入失败时，窗口会显示失败原因，已写出的数据保留在本轮目录中。CSV 每秒刷新一次缓冲，正常停止会关闭文件；异常退出仍可能损失最后尚未刷新的内容。若程序异常中止，`metadata.json` 可能仍标为 `recording`，不能将这种目录当成正常结束的记录。

## 最小验证方法

执行目录：仓库根目录。前置条件：按中文 README 安装项目依赖和子模块，并配置好所选游戏。

```powershell
.\.venv\Scripts\python.exe run.py
```

手动记录 10 秒并停止、导出 ZIP。预期采样数非零，ZIP 包含表中基础文件；元数据里能看到驾驶者和对照名称，CSV 的真实零输入与空白通道可区分。若附带调教文件，原文件应保持原样，分析包中的副本有对应摘要。

再分别验证暂停/恢复和 API 重启：预期暂停期间没有补零行，恢复后的首行标为不连续；重启或切换接口后，原记录已经结束，导出文件仍可读取。使用两个昵称分别记录，预期会生成两个独立目录。

本次仅做调用链、文件生命周期、字段来源和 Git diff 静态复核，没有运行游戏、应用、测试、构建、lint 或类型检查。未执行测试，由用户自行验证。
